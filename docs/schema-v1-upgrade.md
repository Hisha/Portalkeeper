# Schema v1 migration and upgrades

Portalkeeper 0.2.0 consumes the public contract generated by mod-realm-config. It does not modify that module, access AzerothCore databases, or distribute WoW assets. The canonical typed `RealmInfo` contains schema version, realm display fields, connection, `ClientRequirements`, minimum launcher version, service URLs, and dynamic `Addons`/`Patches` collections. The flat service properties preserve existing view/service consumers; raw INI access is confined to parsing and legacy bootstrap.

## Persistent data

Windows: `%APPDATA%\Portalkeeper\` holds existing settings, GitHub metadata, personal addon sources and feed caches. New persistent realm files live in its `realms` subdirectory. Windows application binaries normally live in `%LOCALAPPDATA%\Programs\Portalkeeper`.

Linux: .NET `SpecialFolder.ApplicationData` remains the base, normally `$XDG_CONFIG_HOME/Portalkeeper` or `~/.config/Portalkeeper`. Realm files live in `realms`. Installed binaries remain `$XDG_DATA_HOME/Portalkeeper-app`, normally `~/.local/share/Portalkeeper-app`; the desktop entry is in the adjacent `applications` directory.

Client selection and preferences keep the existing JSON format and location. A temporarily invalid client does not erase the saved selection when preferences are saved. Realmlist/addon/patch backups and addon commit records remain under `<WoW>/.portalkeeper`. No upgrade removes unrelated addon folders, SavedVariables or patch files.

## Legacy realm files

Discovery prioritizes valid persistent Schema v1 realms, including when an earlier release left a legacy file in the store. When no persistent realm exists, discovery checks the working directory/executable and their config children. A single adjacent Schema v1 file is copied and retained at its original location. A legacy file is loaded directly and is never replaced by migration. Multiple candidate realms still require an explicit selection.

Files with `[Server]` and no `[Config]` use legacy compatibility mode. Name/address and TCP ports are validated; absent ports default to 3724/8085. Client validation remains 3.3.5a/build 12340. Existing optional feed URLs are retained when valid; no Schema v1 addon/patch requirements are invented. The saved client selection and normal realmlist/launch path remain available with a valid client.

`[Updates] UpdateURL` is the automatic bootstrap source. Downloads pass the existing strict Schema v1 parser (including minimum version, components, URLs, paths and hashes) before being staged and committed without overwriting another file. The destination uses the source filename in the persistent store, with a .schema-v1 suffix (and numeric suffix if needed) on collisions. The original remains byte-for-byte intact, including a legacy file already in the persistent store.

Missing/unreachable URLs, rejected downloads and persistence failures retain a usable legacy realm with a visible **Legacy compatibility mode** explanation. **CHECK AGAIN** remains available to retry. Network success is not a launch requirement. Only an unusable legacy connection/configuration prevents this fallback.

After migration, discovery uses the persistent Schema v1 copy. The old UpdateURL is not fetched again through the normal startup path. Only the v1 `[Services] ConfigURL` drives ordinary refreshes, which continue to preserve last-known-good data and create unique backups before replacement.

## Windows installer upgrade

1. Close Portalkeeper and run the newer `Portalkeeper-Setup-<version>.exe` as the same Windows user.
2. Inno Setup uses unchanged AppId `{64CF5E71-169A-422C-86D5-AC9A62E0AEEE}`, per-user privileges and previous installation directory. It updates application payload and shortcuts in place. Do not uninstall first.
3. Existing `%APPDATA%` state and user-created realm files are not deleted. The package contains only `example.realm.conf`, which discovery ignores.
4. First launch loads any historical adjacent realm file and attempts migration above. The selected client and existing addons/patches remain intact.

The installer has no WoW installation/deletion steps and no user-specific migration logic. Windows upgrade behavior has been reviewed in the Inno script; native installer execution requires Windows and Inno Setup.

## Windows standalone upgrade

1. Close Portalkeeper. Extract the complete newer ZIP over the existing standalone application directory, replacing application payload while retaining your user-created realm files and backups.
2. Run the new `Portalkeeper.exe`. Existing `%APPDATA%\Portalkeeper` state is discovered, and an old adjacent realm is imported on first launch.
3. After first successful import, future versions can be extracted to a different folder: persistent state is independent of binaries.

If moving to a different folder for the first upgrade from the experimental release, copy your existing `*.realm.conf` into `%APPDATA%\Portalkeeper\realms` (and retain the old folder until successful migration). The old application never recorded arbitrary portable installation locations, so a new executable cannot discover a realm left in an unrelated unknown folder. Do not delete the old download directory first.

## Linux upgrade

1. Close Portalkeeper, extract the newer Linux ZIP, and run `bash install.sh` from that extracted folder.
2. The installer verifies dependencies and ownership marker, stages replacement binaries, copies the old config directory, root realm files and `.portalkeeper` backups into the stage, then swaps the application directory. Existing config wins over bundled defaults. A failed staging/replacement retains/restores the old installation.
3. The same desktop entry is refreshed. First launch imports the retained realm and bootstraps Schema v1. Settings in the separate XDG config location and the selected WoW tree are untouched.

Direct Linux ZIP use follows the standalone rule: preserve/copy an old adjacent realm for the first migration, then use the persistent realm directory for subsequent upgrades.

## Validation and limitations

GitHub Ref accepts branches and tags, including release tags or full refs. It does not interpret arbitrary GitHub release-page URLs as refs. API rate limiting retains the existing public Git advertisement/archive fallback, but an explicit ref is never silently replaced by HEAD. Existing folders with a top-level .toc are recognized without requiring old launcher bookkeeping. Known version/commit updates gate required addons; unavailable remote metadata is reported, source/ref-scoped cached versions retain known update checks, and locally valid existing installs remain usable when no update is known. HTTP addons have no schema hash/version field, so their automatic check is local presence/TOC; users can explicitly use REINSTALL / UPDATE to update them.

Patch validation checks SHA-256 when provided, otherwise existence. Hashless patches need an explicit install/repair action to refresh. No automatic component downloads occur on launcher upgrade. Required readiness is rechecked before realmlist writing/launch. Optional HTTP status and manifest schemas are not invented: URLs are stored, TCP health is retained, and the realm INI owns component policy.

Safety checks assume the selected WoW tree is not concurrently modified by another process while an operation is writing it. Static symlink/junction paths are refused; this is not an operating-system isolation boundary against a hostile local process racing filesystem changes.

## Verification

Run `dotnet build -c Release`, `dotnet run --project tests/Portalkeeper.Tests -c Release`, and `bash tests/install-linux-upgrade.sh`. The regression executable needs a loopback socket for real HTTP download tests and uses only temporary test data. No external realm downloads or real WoW installations are needed.

Publish with `bash scripts/publish-linux.sh` and `pwsh scripts/publish-win.ps1 -Installer`. The Windows installer additionally requires ISCC/Inno Setup; cross-publishing a Windows binary on Linux does not prove native Windows upgrade behavior. Actual results for this change are recorded in the delivery report.
